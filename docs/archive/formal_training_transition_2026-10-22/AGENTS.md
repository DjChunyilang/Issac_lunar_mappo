# 项目工作入口

## 工作模式：优先获得有效实验反馈

- 后续修复在项目现有整体框架内进行；通信、网络、奖励、训练只是例子，不是可调整范围的白名单。可按证据修改现有环境、感知／观测、动作表达、决策时序、规划／控制、安全接口及其他已有组成的实现与配置，也允许必要的内部重构。避免通过不断叠加独立子系统、外置行为补丁或旁路流程解决问题；边界按架构职责判断，不按文件数量判断。历史候选不默认启用，必要的接口语义变化仍须保护旧结果和checkpoint。
- 按下一步实验要回答的问题决定实现和验证范围，采用足以支持该决策的最小方案。
- 每项任务先明确目标行为、最小验收和结束条件；达到后立即推进。新增阻塞项必须指出具体缺陷及其对下一步实验的影响，不能只以“更稳妥”或“覆盖更全”为由追加。
- 一般失败允许带入实验。成功率低、复杂场景失败、性能不足和覆盖不全可以成为结果；只有使当前实验无法运行、数据失真或比较失效的问题才阻塞该实验。
- 围绕实际输入和明确契约编程。不为假想异常增加兼容层、重复检查或回退链；内部错误直接暴露，不用静默回退掩盖缺陷。
- 普通修复不自动新增版本、配置和入口；仅在接口、数据或行为语义确需隔离时版本化，保留历史结果的可复现性。
- 每轮诊断只回答一个具体问题，预先设定范围和预算；已有证据足以决定下一步时停止诊断，不无限追求根因解释或边界覆盖。
- 汇报直接给出结果、判断和下一步；只说明会改变当前决策的限制，不反复罗列“尚不能证明什么”，不把未验证等同于不能推进。

## 开始前

- 检查分支、提交和工作区修改，保留用户已有内容。
- 先读 `docs/current_status.md`，了解事实与暂停条件。
- 再读 `docs/implementation_plan.md`，识别下一步任务及真正相关的前置条件；工作顺序按本文件最新约定执行。
- 架构入口是 `docs/architecture/planning_pipeline.md`。
- 接口入口是 `docs/interface_spec.md`。
- 只加载当前任务涉及的代码、配置、测试和运行手册。

## 当前执行面

- **后续每次启动或恢复训练，都必须使用 TensorBoard 实时监控并保存 events**，覆盖正式训练、短程对照、学习探针及离线拟合。启动或复用本地 TensorBoard 服务，向用户提供访问地址、日志目录与查看命令，并确认 events 已生成且随训练更新；训练结束后保留日志供回放。缺少依赖或不可写时不能静默关闭日志。
- TensorBoard 使用独立 run 目录，记录配置、横轴单位和恢复边界。T11 以实际底层环境步为横轴，评估步单独记账；离线拟合以优化器步为横轴。具体接线与命令见 `docs/references/output_management.md`。
- 活跃代码与配置索引位于规划架构文档，不在这里复制参数。
- 事实以代码、有效配置和可追溯测试／评测记录为准。
- 区分已实现、契约测试通过、完整闭环通过和研究建议。
- 历史配置及实验入口保留复现价值，不能默认启动。
- 训练按用户授权范围及相应阶段的最小准入条件推进；已有授权满足条件后直接执行，不重复请求许可，不自动扩大训练预算。

## 修改与验证

- 保持版本隔离，不能静默改变历史配置或 checkpoint 的语义。
- 只更新实际受影响的代码、接口、架构或迁移说明，不把局部修改扩展为全仓整理。
- 默认只验证受影响行为；修复缺陷时复现该缺陷。仅在发现相关失败或实际依赖变化时扩大验证，不为低影响修改或实现细节补形式化测试。
- 简单文档修改只检查内容和 diff，不运行算法测试或全仓检查。
- 测试失败保留日志；被跳过的必要测试不能计为通过。
- 已有有效证据继续复用；无关文件或源码指纹变化不自动触发全套重跑，以实际行为和依赖影响决定补测范围。
- 修改后检查 diff；实际运行实验时在实验记录中保留命令与证据路径，纯工作规则修改无需另建实验记录。
