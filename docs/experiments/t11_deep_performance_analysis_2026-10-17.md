# T11优化后深度性能分析（2026-10-17）

## 结论与范围

本轮回答“已有约8倍加速后，为什么CPU平均仍仅1.89逻辑核、GPU约5%，下一步该优化什么”。不修改训练算法或有效配置，不恢复训练。基准仍是A1、seed23、2环境×4车、K512两轮、40步/8秒、FP64、`update_000008.pt`运动恢复点。原生记忆、共享安全几何、6线程已经实现，不能再列作新方案。

当前瓶颈已经分散，约一半关键路径在主线程的串行阶段，另外一半等待三类worker任务完成。优先消除不可变地形的重复复制/建树和规划评分重复打包，再批处理安全约束与融合预测，随后发展常驻环境进程、跨环境流水线。GPU深度常驻和扩大全环境批量适合后续阶段，GPU利用率本身不作为优化目标。

本轮双独立collector容量探针得到**1.53倍总吞吐**，CPU平均189%→312%、GPU约5%→9.4%；并行空间确实存在，但也有并发成本。它不是已实现的生产多进程环境，更不代表正式训练已改变。

## 第一优先：不可变地形复用与评分打包

### 冻结请求不应重建同一地形

`upstream_queue.py:44`执行`terrain.snapshot() → FootprintTerrain(...)`，复制数组并新建cKDTree；`UpstreamPlannerInput`随后又用snapshot检查时间。旧view本身已经只读，记忆更新发布新view，pending应该保留信息时刻旧view，不需要复制其几何。

建议使用内部不可变fork，独立维护时间/见证缓存、共享只读坐标/属性/KD树；公开`snapshot()`仍返回脱离内部状态的数据。内部只读校验改直接读取不可变数组，涉及`upstream_planning.py:143`、`upstream_safety.py:88,111`、`upstream_flat_review.py:25,252`、`upstream_observation.py:76`等。

串行函数诊断观察到1201次`snapshot()`、124次`FootprintTerrain`构造；这些次数用于说明重复工作，不将插桩累计时间当作6线程占比。请求冻结本身0.576 s，是该阶段可改善空间的上限，不是保证收益。

最小验收：capture后继续运动感知、添加危险点及刷新时间戳，pending仍保留原信息时刻的全部值；4宏步控制/动作/奖励/记忆/消息/RNG配对一致。

### 4次规划为何打包36次

当前三次计时均为：`plan_batch` 4次、`pack` 36次、`LocalTerrainBatch`新建36次。打包总计0.708 s，其中地形构造0.591 s。

额外32次来自`upstream_planning.py:359 _output → upstream_mppi.py:398 score_trajectory → pack([item])`。HOLD/刹车有效输出与MOVE选定输出都会评分。每次单车评分还覆盖共享kernel的`_packed_terrain`，破坏整批缓存；这是现有“GPU常驻缓存”在实际调用链中的缺口。

建议先把最终轨迹评分集中批量执行，或者传入本轮已有地形/邻车行视图；单车评分缓存与整批规划缓存分开。保持最终实际轨迹的重新评分，不能直接套用采样候选分数，因为最终控制可能经过截断、延续或停车处理。HOLD输出也必须保留评分与诊断。

仅地形打包和请求冻结合计约1.17 s，占当前15%；不能仅靠这两项承诺再翻倍。共享不可变视图还可能影响其他阶段，须由整轮回放量出净收益。

## 第二优先：安全约束批处理、停车预测去重

`upstream_safety.py:159–165`在三个模式内按边对循环，反复调用小型`det/solve`。执行器法向量和边对矩阵由spec与是否存在speed_cap决定，可缓存原顺序边对、矩阵及非奇异mask；每次批量求交点、筛可行顶点并剪枝。先保留原NumPy/LAPACK和OSQP，再决定是否将整段移入原生CPU。

`_geometry_constraints`仍逐个处理9个扫掠时刻。可以保留原算术顺序构造查询点，再合并一次KD查询；邻车初始位置、半径和初始CBF值可以提到循环外。安全投影阶段总计1.617 s，不等于这些子项都可消除。

`_verify:177–181`先调用`stop_envelope`，后者已经积分停车轨迹；随后补零控制又从头`rollout_numpy`。建议生成停车控制后仅积分一次，或复用已算轨迹并补齐后续静止段。保留完整40步/8秒轨迹与动态复核、首失败原因及停车证明，不缓存动态最终验收结论。

后续可以把停车控制序列和CPU预测融合成一次原生调用，减少逐步Python→ctypes→地形查询。先在严格支持见证成立的平坦路径验证，再扩展非均匀地形。最小验收比较最终约束A/b及行序、OSQP状态/残差/控制、完整轨迹数组与首失败；优先复用现有安全和运动回放测试。

## 第三优先：记忆分配、索引与阶段融合

记忆虽已原生化，仍有全旧点cell重算、每帧重建两个哈希表、cell内小vector分配，以及原生输出经过TerrainSnapshot和FootprintTerrain的再次复制。建议依次：

1. 以不可变几何身份缓存cell；使用连续索引和原生scratch减少小分配。
2. 内部构造接管独占输出缓冲区，避免重复复制；仍被pending引用的旧buffer不得复用。
3. 将每车`memory.observe → 新view上的execution_prediction → parking report → 中心特征查询`合为一个任务，只保留一次完成屏障。radio快照在新pose/now、发布新消息之前冻结，按原顺序提交。

当前每宏步5 tick，每tick安全/记忆/预测三次批量屏障，至少15次；合并阶段可减少主线程调度和重复中心查询，但不能移除同一环境内的真实时序依赖。

### 生产实现建议

每个环境由常驻进程持有地形、索引、复核缓存和状态，进程间交换已定动作、观察和必要规划数组，不每tick pickle完整地形。主进程仍按原`[2,4]`形状采策略动作，保留A1先全批HOLD、再MOVE Normal的全局RNG顺序；环境ID和各车MPPI RNG不重编号。

GPU由统一服务批量处理请求，避免多个独立kernel缓存互相覆盖。环境之间可以错开CPU计算和GPU/CPU复核，但同一环境广播、任务、奖励和控制生效顺序不变。先实现2个owner、每个2或3worker，量IPC字节、PSS及关键路径；不是简单替换为ProcessPool.map，也不从每进程6worker起步。

## GPU的下一步和扩批边界

当前12次`evaluate`累计约0.424 s，占总时间5.44%。只让这一段无限快，端到端最多约1.058倍；这不是全部GPU路径的上限，但足以说明单独打磨已有预测核不能解决主要瓶颈。

GPU建议顺序：复用打包/集中评分 → 合并候选及诊断下载 → CUDA events延后读取阶段计时 → 按车维护地形索引/设备buffer并更新变化区域 → 批量CPU/GPU流水。正常两轮规划现有12次显式全设备同步，另有标量隐式同步；其中只用于计时的屏障可以延后，但真实数据依赖、deadline和错误检查不能删除。

`_cap_curves`虽然源码有40轮小GPU计算路径，本轮36次调用总计仅2.5 ms，**降为低优先级**；不能因为代码看起来低效就排到当前热点之前。复杂地形的非均匀40步融合另做专项，不能把平地结果外推。

为了持续提高GPU批量，可以在上述优化后测试2/4/8/16环境的“转移/s—CPU—GPU—内存”曲线，达到收益平台或内存边界即停止。**增加环境数改变训练协议**：2×128变成4×128会改变批量/更新频率；即便改4×64保持256转移，也会改变GRU/GAE截断和RNG消费。必须作为独立采样协议保存，不能静默迁移旧checkpoint。PPO期间提前采下一批同样改变当前同步on-policy流程。

当前不优先迁移小批策略/PPO、继续盲加线程、降低K/时域或FP64；先把实测重复工作和串行关键路径处理掉。
